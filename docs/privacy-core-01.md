## Поведение

`/privacy` доступна без авторизации. `/privacy?garden=<UUID организации>`
добавляет только опубликованные публичные документы указанного оператора,
без списков пользователей или данных организации. Общая страница отдельно
объясняет контексты сада и поставщика. Пустая конфигурация показывает отсутствие
утверждённых документов. Ошибка загрузки не подменяется готовой политикой.
Ссылки есть на входе, активации, восстановлении, сбросе пароля и входе PLATFORM_OWNER.
Без безопасно установленного контекста сада общий вход не подставляет чужую политику.
Организационный документ до сбора реальных данных всё равно должен быть доступен
по правильной публичной ссылке/точке входа — это часть будущей приёмки.

`/privacy-center` доступен всем четырём tenant-ролям. Он показывает документы,
оператора, реестр, разрешённые сведения об оригиналах и собственные обращения.
Директор дополнительно получает очередь обращений своей организации;
ADMIN не получает чужие обращения. Воспитатель видит только собственные согласия,
без доступа к согласию родителя даже при назначении на группу. Родитель видит свои
записи и записи связанного активного ребёнка, где именно он указан представителем.
Запись другого представителя того же ребёнка не раскрывается. Архивация связи
закрывает доступ к детскому контексту согласий и обращений. PLATFORM_OWNER не
получает tenant-доступ через свою cookie.

### Документы и реестр

Документ хранит неизменяемые UUID, тип, версию, точный текст, SHA-256,
контекст оператора, дату и ссылку утверждения, дату действия. Публично выдаются
только `published` с завершёнными реквизитами/утверждением, верным хешем и
наступившей датой действия. Draft/retired исключены из публичной выдачи.
Историческая версия остаётся в разрешённой записи согласия. Новая версия
документа не создаёт согласия и не переписывает старые свидетельства.

В приложении **нет HTTP-операции утверждения/публикации**. Директор не может
назначить себе юридическое основание. Реестр включает утверждённые версии из
защищённого каталога и явную техническую инвентаризацию ещё не согласованных целей.
У неё основание, хранение, необходимость согласия, подрядчики и места равны `null`,
а не вымышленным юридическим значениям. Роли в технической инвентаризации не
предоставляют доступ: действующие backend-проверки остаются источником прав.
Переписка ограничена участниками; директорская роль в инвентаризации не даёт чтения
чужих личных диалогов. Отложенных целей и модулей в списке разрешённых целей нет.

Для будущего заполнения используется защищённый JSON bundle и команда из `backend/`:

```sh
python -m app.cli.privacy_catalog /protected/reviewed-catalog.json --reviewed
```

`--reviewed` записывает предоставленное ответственным лицом утверждение; команда
не проверяет юридическую истинность реквизитов и не заменяет юриста. Поля и типы
заданы `CatalogInput`, `DocumentInput`, `PurposeInput` в `services/privacy_catalog.py`.
Bundle не содержит секретов, паспортов или сканов. Не включать в Git непубличные
материалы проверки. Сначала требуется содержательная внешняя юридическая приёмка.

`privacy-catalog.draft.example.json` — только синтетический **непубликуемый** пример.
Его UUID организации необходимо заменить UUID отдельной синтетической организации.
Импорт без `--reviewed` допускает только черновики и выключенные цели; пример не
разблокирует приглашения. `synthetic: true` отвергается в staging/production.
Поле `organization_id: null` допустимо только для собственной политики поставщика,
не означает wildcard на документы садов. Цели всегда принадлежат конкретной организации.

Версии документа и цели неизменяемы; для утверждённой редакции используются новые
UUID и версия. Для снятия старой редакции повторно передаётся её полная неизменённая
карточка со статусом `retired`. Переход обратно запрещён. Импорт атомарен;
публикация/снятие tenant-документа сериализованы с записью свидетельств и приглашениями.
PostgreSQL-триггеры запрещают UPDATE/DELETE документов, целей, подтверждений,
оригиналов и событий; документу разрешено только published → retired.
Будущая законная процедура удаления свидетельств требует отдельной приёмки жизненного цикла.

### Приглашения и согласия

Перед приглашением уполномоченный сотрудник выбирает утверждённую цель
`account_access` и отдельным действием подтверждает проверку внешних документов.
Записываются сотрудник, время, организация, профиль и неизменяемая версия основания.
Путь «email → письмо → пароль → вход» сохраняется. Сервер проверяет действительность
основания и для повторного, legacy teacher и массового приглашения.
Массовый предварительный расчёт отдельно показывает отсутствие подтверждённых документов.
Существующие аккаунты продолжают входить без универсальной галочки.
Подтверждение сотрудника **не создаёт согласие** и не является электронной подписью.

Запись бумажного оригинала разрешена DIRECTOR/ADMIN только для включённой,
утверждённой цели с `consent_required=true` и отдельным документом `paper_consent`.
Обязательны дата получения, конкретный субъект, представитель для ребёнка,
проверка полномочий подписанта и наличия оригинала в организации. Это учёт
результата внешней проверки, не автоматическое доказательство юридической силы.
Дата проверяется в часовом поясе организации, не в UTC и не по часам браузера;
она не может предшествовать действию/утверждению документа или быть в будущем.
Ответственный — аутентифицированный автор записи; IP/устройство не собираются.
Нет файлового API, паспортных полей, подписи или скана.

История append-only: `recorded`, `withdrawn`. POST-запись идемпотентна по автору,
организации и UUID запроса; повтор ключа с другим содержанием отвергается.
Конкурентные операции сериализуются PostgreSQL-блокировкой tenant root.
Дубли активного оригинала одной версии отвергаются. Отзыв покрывает предыдущие
версии той же цели, субъекта и представителя; повторный отзыв не дублирует событие.
Новое согласие после отзыва требует нового бумажного оригинала с более поздней датой
(при точности даты до дня повтор в тот же календарный день организации намеренно закрыт).
Отзыв не завершает сессии, не уничтожает карточки/посещаемость и не отключает
работу, имеющую самостоятельное основание. Новые необязательные операции или
OFF-модули эта задача не включает и не разрешает.

### Обращения

Пять типов: сведения, исправление, отзыв, прекращение обработки, законное удаление.
Заявитель и организация определяются сессией. Детский контекст разрешён только
родителю с текущей активной связью; существующая связь не объявляется универсальным
доказательством законного представительства. Получатель — оператор организации,
очередь директора, без доступа поставщика к содержимому tenant-запросов.

Минимальные поля: тип, непрямые идентификаторы, автор, время, статус и история.
Свободного текста, вложений и автоматической выгрузки данных нет. Дополнительные
сведения и ответы передаются только по отдельно подтверждённому каналу оператора.
Пока он не задан, приложение прямо сообщает об отсутствии утверждённого контакта.
Запись обращения не считается его юридическим исполнением.

Статусы: submitted → verifying → in_review → completed/declined;
отказ после verifying также разрешён. Директор задаёт срок после правовой
классификации; система показывает обращения без срока и просрочку, не выдумывает
сроки по закону. Для закрытия нужны фиксированный код решения и подтверждение
ответа по проверенному каналу. Проверяется ожидаемый предыдущий статус, поэтому
конкурентное устаревшее изменение отклоняется. completed не выполняет никаких
изменений/удалений/экспортов бизнес-данных.

## Privacy/security review новых функций

Все новые субъектные запросы tenant-scoped; клиент не передаёт организацию или
заявителя. Родительские связи проверяются при каждом чтении/отзыве. Нового
универсального чтения детских данных для TEACHER или PLATFORM_OWNER нет.
Сохраняются origin-проверка и cookie-аутентификация. Privacy API отдаёт `no-store`
и `no-referrer`; protected данные не сохраняются в browser storage. Тексты документов
рендерятся как текст, не HTML. Общий журнал содержит только фиксированное действие
и непрямой идентификатор, без контактов, тела обращения, текста согласия и токенов.
Ошибки валидации и CLI не выводят поступившие реквизиты, SQL-параметры и секреты.

Проверки включают две организации, четыре роли, несвязанных/бывших представителей,
подмену субъекта и версии, запрет сканов, даты, повторы, PostgreSQL-конкуренцию,
историю, отзыв без удаления/блокировки входа, default OFF boundary и старые приглашения.
Браузерные проверки включают публичную страницу 390px, четыре роли, отдельное
подтверждение документов, обращения и учёт/отзыв оригинала.
Полный backend/PostgreSQL/migration/frontend/browser/security/Docker CI обязателен
на финальном HEAD PR. Его фактический результат фиксируется в PR, не предполагается из этого документа.

## Что ещё нужно для реальных данных

- Настоящий поставщик и его юридический статус, каждый оператор, проверенные
  реквизиты/контакты, полномочия и разграничение собственных/порученных целей.
- Утверждённые политики обеих сторон и основания по каждой цели; необходимость,
  форма и порядок проверки согласия/полномочий представителя.
- Оформленное поручение, когда требуется; проверка юристом применимой модели
  частного/государственного/муниципального учреждения. Эта задача договоров не создаёт.
- Подтверждённые хостинг, локализация РФ, резервные копии, почта, субподрядчики,
  трансграничные потоки и договорные обязанности.
- Сроки/условия хранения, архивирование/удаление, обработка запросов вне кабинета,
  проверка личности, каналы ответа, назначенные ответственные и инцидентные процедуры.
- Уведомления РКН либо документированная применимость исключения; модель угроз,
  организационные и эксплуатационные меры защиты, управление доступом/секретами,
  независимая юридическая и security/ops-приёмка.

Пока эти сведения и приёмки отсутствуют, работа с реальными данными запрещена.
