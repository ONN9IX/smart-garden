# Stage 3 — модель данных и решения

**Источник:** `docs/04-mvp-roadmap.md`, `docs/05-personal-data-baseline.md`, `docs/06-product-scope.md`; Stage 2 в `main`.  
**Область:** карточки сотрудников и ручная посещаемость. Этот документ уточняет черновой roadmap при расхождении.

## 1. Границы

DIRECTOR и ADMIN ведут сотрудников и ежедневно отмечают посещаемость детей своего сада. PARENT остаётся на техническом экране. TEACHER, СКУД, планшет, медицинские причины отсутствия, табель рабочего времени и автоматическая регистрация прохода не входят в Stage 3. Данные dev/test/preview только синтетические.

Единственная БД — PostgreSQL. UUID, `/api/v1`, server-side session, HttpOnly cookie, Argon2id и общий формат ошибок сохраняются. Backend определяет роль и организацию по сессии; `organization_id` из запросов запрещён.

## 2. Employee и User

Карточка `Employee` хранит `id`, `organization_id`, `user_id nullable unique`, `first_name`, `last_name`, `middle_name nullable`, `position` (1–100 символов), `status active|archived`, `archived_at`, `created_at`, `updated_at`. ФИО и должность после trim; пустое отчество → null. Адрес, дата рождения, телефон, email, паспорт, зарплата, медицинские сведения и заметки не собираются.

`Employee.user_id` связывает карточку с ровно одной учётной записью при выдаче доступа. Nullable нужен для обычных сотрудников без доступа и для уже существующих DIRECTOR/ADMIN, созданных до Stage 3. Создание карточки само по себе **не выдаёт доступ**. DIRECTOR может создать для активного Employee только `User(role=ADMIN)` с случайным глобально уникальным username и одноразовым временным паролем. Существующую учётную запись DIRECTOR нельзя создать или привязать через этот API. ADMIN может вести карточки сотрудников, но не создавать, блокировать, разблокировать или сбрасывать их учётные записи. Это не вводит TEACHER преждевременно.

Для учётной записи: один Employee ↔ максимум один User; создать вторую нельзя. Пароль показывается только в ответе create/reset, хранится только Argon2id hash. Reset инвалидирует старый пароль и все сессии, ставит `must_change_password=true`; blocked остаётся blocked. Block и archive Employee отзывают сессии и блокируют связанного ADMIN в одной транзакции. Поэтому архивировать карточку со связанным User может только DIRECTOR; иначе ADMIN смог бы обойти запрет на блокировку чужого аккаунта. Restore Employee не разблокирует User. Unblock возможен только при активном Employee. ADMIN не может повысить себя или другого пользователя; изменение роли существующего User в Stage 3 отсутствует.

## 3. Attendance

`Attendance` хранит `id`, `organization_id`, `child_id`, `group_id` (снимок группы на дату первой отметки), `date` (календарная дата сада), `status present|absent|unknown`, `arrival_time nullable`, `departure_time nullable`, `created_by` и `updated_by` (User UUID), `created_at`, `updated_at`. Уникальность `(child_id, date)` и индексы `(organization_id, date, group_id)` и `(organization_id, date, status)`.

Снимок группы не меняется при переводе ребёнка: прежняя посещаемость остаётся в прежней группе. Дата передаётся `YYYY-MM-DD` без преобразования в UTC; время — местное настенное `HH:MM` для выбранной даты. В Stage 3 не записываются автоматические события входа. В будущем терминал потребует отдельной модели timestamp + источник события и явной временной зоны сада; нельзя переинтерпретировать старые ручные значения как точные события прохода.

На экране дня отсутствие записи означает `unknown`. Явная отметка `unknown` сохраняется в строке, чтобы зафиксировать исправление и автора. Отмечать можно только активного Child текущего tenant; дата не может быть в будущем. `present` допускает времена без обязательного заполнения; `departure_time` без `arrival_time` запрещено, а при обоих значениях departure ≥ arrival. `absent` и `unknown` требуют оба времени null. Интервал через полночь этим модулем не моделируется. Upsert одной пары child/date атомарен. Архивация Child сохраняет историю; новые отметки ему запрещены. Архивация Group не изменяет старые снимки группы.

Свободный `comment` из предварительного roadmap **отложен**: в нём легко записать диагноз, обстоятельства семьи или иные избыточные сведения. Причину отсутствия Stage 3 не собирает. При необходимости позднее вводить только специально согласованные структурированные категории после проверки ПДн.

## 4. Доступ

| Действие | DIRECTOR | ADMIN | PARENT |
|---|---|---|---|
| Читать, создавать и редактировать карточки своего сада | да | да | нет |
| Архивировать карточку без аккаунта | да | да | нет |
| Архивировать карточку со связанным User | да | нет | нет |
| Создать/сбросить/блокировать ADMIN account сотрудника | да | нет | нет |
| Читать и отмечать посещаемость своего сада | да | да | нет |
| Видеть данные другого сада | нет | нет | нет |

Чужой UUID → `404 NOT_FOUND`, независимо от типа чужой записи. Отсутствие права по роли → `403 FORBIDDEN`. Нельзя передать tenant или автора отметки в body. Все management маршруты используют `require_role`, а объектные запросы фильтруют по organization текущего User.

## 5. Персональные данные и 152-ФЗ

- Цель Employee: учёт сотрудников и управление выданным доступом; цель Attendance: ручная отметка присутствия ребёнка. Поля ограничены этими задачами.
- Директор/администратор видят только свой сад; PARENT и сотрудники без аккаунта не видят модуль. Учётная запись ADMIN даёт операционный доступ по существующей модели; TEACHER доступ не подразумевается.
- Не передавать ФИО/должность/посещаемость во внешнюю аналитику, console или access logs. Не класть ПДн в URL; в URL допустимы UUID, дата, enum-фильтры. Временный пароль только в памяти UI до закрытия карточки, без browser storage.
- В dev/test/seed запрещены настоящие данные. До реального пилота отдельно определить оператора, основание обработки, сроки хранения, порядок исправления/удаления, инфраструктуру и потоки данных по действующим требованиям 152-ФЗ. Техническое ТЗ не заменяет правовую проверку.

## 6. Критичные сценарии

1. DIRECTOR создаёт карточку, выдаёт ADMIN доступ, получает временные данные один раз; новый ADMIN меняет пароль и видит только свой сад.
2. ADMIN создаёт обычного сотрудника без доступа, но не может выдать ему роль или управлять чужой учётной записью.
3. DIRECTOR блокирует/архивирует сотрудника: сессии связанного ADMIN отозваны; restore карточки не разблокирует User.
4. Два сада могут иметь одинаковые ФИО/должности, но не читают и не изменяют карточки друг друга.
5. На выбранную дату отображаются дети активной группы со статусом `unknown`, затем ручная отметка `present`/`absent`; повторная отметка обновляет ту же запись и `updated_by`.
6. Перевод ребёнка не переносит старую посещаемость в новую группу; архивация сохраняет историю. Чужой/архивный Child и дата в будущем отвергаются.
7. PARENT не получает API сотрудников/посещаемости и не видит их в навигации.

## 7. Миграции и rollout

После 0006: 0007 `employees`, 0008 `attendance`. Обе имеют upgrade/downgrade. Новые nullable связи не меняют существующие Stage 2 записи. Не изменять прежние credentials или child records при миграции. Сначала API contract и миграции, затем вертикальные срезы Employee и Attendance, затем браузерная интеграция и Docker preview.
