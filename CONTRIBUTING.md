# CONTRIBUTING — Умный сад

Этот файл описывает единый способ работы с кодом. Роли Frontend/Backend могут меняться между этапами.

## Перед любой задачей

1. Прочитать GitHub Issue.
2. Проверить `docs/00-development-guide.md`.
3. Если задача касается API — проверить `docs/03-api-contract-v0.1.md`.
4. Если задача касается окружения/доступов — проверить `docs/08-team-access-and-environments.md`.
5. Обновить `main`.
6. Создать/переключиться на отдельную issue-ветку.

## Нельзя

- работать напрямую в `main`;
- менять API только на одной стороне;
- добавлять вторую БД;
- коммитить secrets;
- использовать реальные ПДн;
- оставлять настройку только на своём компьютере;
- merge PR с красными тестами/lint/build.

## Перед Pull Request

Backend:
```bash
ruff check .
pytest
```

Frontend:
```bash
npm run lint
npm run build
```

Если команда пока ещё не существует на текущей ранней задаче, это явно указывается в PR.

## Комментарии в коде

В каждом вручную созданном нетривиальном source-файле сверху должен быть короткий комментарий/docstring:
- назначение файла;
- откуда приходят данные;
- что файл возвращает/меняет;
- важное ограничение безопасности/tenant, если есть.

Не комментировать очевидный синтаксис. Комментарий должен объяснять **почему**, контракт или ограничение.

Generated-файлы, package-lock, migrations auto-generated sections и простые index/export files не требуют искусственных комментариев.

## Ошибки

- Backend отдаёт только общий error contract.
- Stack trace клиенту не возвращается.
- Frontend не показывает raw JSON/exception.
- Ошибки нельзя молча проглатывать.
- В logs нельзя писать password/token/session raw value/лишние ПДн.

## Передача другому разработчику

Работа считается передаваемой только если другой участник может поднять её из Git, используя:
- README;
- `.env.example`;
- Docker Compose;
- migrations;
- seed;
- tests.

Подробно: `docs/08-team-access-and-environments.md`.
