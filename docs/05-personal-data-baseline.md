# Персональные данные — обязательный baseline проекта

Этот документ задаёт технические ограничения для разработки. Он не заменяет юридическое заключение перед коммерческим запуском.

---

# 1. Основной принцип

Каждая функция проверяется по вопросам:

1. Какие персональные данные нужны?
2. Зачем они нужны?
3. Можно ли выполнить функцию без них?
4. Кто должен видеть данные?
5. Кто может изменять?
6. Где они хранятся?
7. Как долго?
8. Что происходит при блокировке/уходе из сада?
9. Нужно ли логировать изменение?

---

# 2. Минимизация

В MVP собираем только данные, которые нужны текущей функции.

Не добавлять поля «на будущее».

Поэтому на раннем MVP:
- email родителя optional;
- телефон optional;
- медицинские сведения отсутствуют;
- биометрия отсутствует;
- фото отсутствуют;
- документы ребёнка отсутствуют.

---

# 3. Dev/Test

Запрещено использовать настоящие данные детей и родителей.

Использовать только синтетические:

```text
Максим Иванов
Анна Петрова
София Сидорова
```

Не копировать production database в локальную среду.

---

# 4. Пароли

Не являются полем, которое администратор может просмотреть.

В БД:
- только password hash.

При reset:
- старый пароль инвалидируется;
- создаётся новый временный;
- временный показывается только один раз;
- при первом входе обязательная смена.

---

# 5. Разграничение доступа

Принцип least privilege.

DIRECTOR не становится Super Admin платформы.

ADMIN не получает право повышать себя до DIRECTOR.

В будущем TEACHER видит только необходимую ему часть данных своей группы.

PARENT видит только связанных с ним детей.

---

# 6. Изоляция садов

Это обязательное security requirement:

```text
Сад A != Сад B
```

Любой запрос к данным проверяет tenant context на Backend.

Frontend filtering недостаточен.

---

# 7. Логи

Нельзя писать:
- passwords;
- password hashes;
- temporary passwords;
- полные auth request bodies;
- лишние ПДн.

Audit Log и технические logs — разные сущности.

---

# 8. Production infrastructure

До пилота с реальными данными необходимо подтвердить размещение систем хранения и обработки с учётом действующих требований законодательства РФ.

Для данных граждан РФ архитектура должна учитывать требования локализации баз данных.

Нельзя по умолчанию подключать зарубежные SaaS для:
- базы;
- файлов;
- логов;
- session replay;
- аналитики;
- error tracking

без отдельной проверки потока данных.

---

# 9. Правовая документация до пилота

Отдельно проработать:

- кто является оператором ПДн;
- какую роль играет компания «Умный сад»;
- договор с садом;
- поручение обработки при необходимости;
- политика обработки ПДн;
- основания обработки;
- согласия, когда они требуются;
- порядок обработки данных несовершеннолетних;
- сроки хранения;
- удаление/уничтожение;
- запросы субъектов;
- уведомление Роскомнадзора, если применимо;
- порядок реагирования на инциденты;
- перечень подрядчиков.

---

# 10. Законодательный ориентир

При разработке учитывать актуальную редакцию Федерального закона №152-ФЗ «О персональных данных», в частности:
- принципы законной, целевой и неизбыточной обработки;
- обязанности при сборе данных;
- требования к безопасности ПДн.

Перед production запуском документ должен быть проверен профильным специалистом по российскому законодательству о ПДн.
